# Runtime seam audit: faster execution without changing the study

Read-only audit of source `ca41bfdb2fd4e4c4c784eabd321ea75e41a45299`, 2026-10-24. This note changes no production source, protocol, ledger, job or old evidence. Scheduler observations belong to the operator; historical PENDING receipts are not current-state proof.

## Decision

The existing committed cue-circuit runner cannot be externally split as-is. Its physical batches are independent, so deterministic splitting is scientifically possible, but requires reviewed execution/provenance/forecast/merge changes. If a whole-study Bridges-2 H100 allocation starts sooner, that avoids the shard registry and merge change. It still requires portability work and a fresh whole calibration; an H200 timing/control receipt cannot release H100 execution.

Do not reduce buffers, cap64, B8/L224, numerical checks, frozen rows or planned contrasts to fit a queue. These do not solve unavailable H200 capacity or an interactive submission limit. The existing main remains authoritative until terminal cancellation and zero-attempt evidence establish that a replacement cannot duplicate attempted work. No cancellation or live-state claim is made here.

## Minimal deterministic parallel shard capability

Keep the generation kernel and scientific payload untouched. Add a separate, frozen execution plan partitioning global batch indices [0,1168) into disjoint half-open ranges, in original order, with exact row-ID/slot lists. Each range must contain whole physical batches. Plan only from full-cap timing and queue/resource information, before any main outcomes; no early-EOS or outcome-based repartition.

A plan must bind frozen scientific hash, new execution source/provenance hash, whole calibration receipt and artifact hashes, shape/cap/precision, GPU hardware/software identity, fixed buffers and margins, exclusive absolute registry, canonical output directory for every shard, and zero-attempt replacement receipt. Claims must be durable and exclusive before model work, using the existing O_EXCL/fsync pattern. Exactly one invocation and output is allowed per shard; duplicate claims, failed/orphan invocations, unapproved outputs or drift poison the scientific release. No retry, range overlap, resume or replacement shard is permitted. Disable scheduler requeue/restarts and check final scheduler receipts.

Each worker validates its own approved active claim, the common release/plan and whole calibration before work; executes its frozen batch slice under its actual allocation Start/End; preserves original attempt/terminal fields and IDs; records shard ownership in a bounded sidecar rather than silently changing the frozen generation schema; validates exact local rows, EOS/cap, logical positions, numerical controls, captures and actual forward counts. An active peer is valid in parallel mode; a failed peer stops further attempts at checkpoints and blocks merge. A peer may complete an already-running forward before seeing failure, which is accounted as attempted work, never retried.

Strict final merge must require exactly the approved invocation/output inventory, one completed claim/outcome for every range, unchanged source/calibration/plan/binding, hashed immutable journals/artifacts and final scheduler success/no restart. It must reject extra, missing, duplicate, malformed or failed evidence. Assemble in original global order and invoke the unchanged full `_coverage` logic through an explicit journal reader mapping, then unchanged `generation_map` before label export. No partial scientific release. A directory union or concatenation alone is insufficient: existing reconstruction checks hashes against protocol, but a new merger must additionally bind each attempt's operations hash to the owning shard operations and reject extra journal filenames/foreign batches.

Prior `sdr_native_controls.py:312-495` offers exclusive claims, immutable outcomes, exact inventory and fail-closed merge patterns, but is deliberately sequential: `_validate_predecessors` requires every earlier shard complete; `_check_active_claim` rejects other outstanding invocations.
