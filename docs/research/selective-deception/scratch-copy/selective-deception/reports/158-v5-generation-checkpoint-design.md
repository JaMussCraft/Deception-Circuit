# V5 batch generation checkpoints: minimal design

Read-only design against reviewed source `9eb2a6a5c8481d99053b78ec2cdc43a3c606cd3c`; no implementation, GPU jobs, API calls or source changes. Scope: frozen historical cohort, existing five states, native generation limits (sandbagging **1024**, despite CLI default 512), unchanged masking/donors/eligibility. Proposed implementation requires new reviewed source and segment receipts; do not relabel the old execution receipt.

## Finding and exact seam

`evaluation/gen_engine.py:301` (`generate_bucketed`) stable-sorts original rows by decreasing prompt length, makes original batches of eight, trims each batch's leading pads, calls `generate`, then retains only `piece[:, keep:]` in RAM. Persist **that raw generated token block immediately after each completed original batch**, before advancing. Resume the same original batch plan and skip completed batches; never filter pending rows and re-bucket them. Batch composition/padding changes can alter BF16 argmaxes.

`evaluation/benchmark_eval.py:370` (`fixed_cohort_screen`) first generates all recipient-intact rows, derives `known` from recipient prompts, then generates the ordered `missing` donor prompts. Until both calls return, no fresh output is persisted. `:352` (`_save_partial`) saves decoded strings only, after a whole state generation; it has no resume reader. Those strings cannot recreate exact donor tokens, EOS positions or coherence. Existing `screen_cache` is the wrong abstraction: fixed-cohort mode deliberately bypasses it and it persists a complete screened object under different eligibility semantics.

The actual shared context is **`EvalContext` + `Session`**, not a `RunContext` class (`evaluation/context.py:410`, `:338`). Session memoizes a completed screen only in process; `ctx.out_dir`, `ctx.cli`, `ctx.node_model`, `ctx.tokenizer`, `ctx.all_gates_open()` and `ctx.circuit(masks)` are sufficient. No context refactor is necessary.

## Smallest implementation surface

1. `evaluation/gen_engine.py`: add optional `batch_store=None` and `stop_after_batch=None` arguments to `generate_bucketed`; defaults preserve every existing caller. Store load/save receives batch ordinal, original row indices, `keep`, `cut`, and generated-token block. Loaded pieces return on the expected device and pass through the existing concatenate/inverse-order reconstruction. Keep all normal validation even when everything is loaded. Stop only after durable save, by a dedicated `GenerationSegmentComplete` exception; never treat an incomplete tensor as successful generation.
2. `evaluation/benchmark_eval.py`: `generate_under` forwards the optional store/stop arguments. Fixed mode supplies separate keys for **recipient-intact**, **native-donors**, and **each non-full config**. The full config reuses recipient-intact tokens; it must not generate again. Recompute `known`, the ordered `missing` donor list, `pool_refs`, partners and corrupt stream with the existing code from restored tokens. Bind each ablated phase to the actual resulting corrupt-token tensor, not only donor IDs. Restrict this feature to explicit fixed-cohort + interchange mode initially.
3. One small `evaluation/generation_checkpoint.py` helper: canonical identity, deterministic batch plan, JSON token storage, validation, atomic commit, explicit segment-stop exception. This is one run's checkpoint folder, not a cross-study cache. No pickle or object deserialization. An exclusive run writer lock prevents two segments writing concurrently; store lock owner/job metadata and require explicit verified stale-lock recovery.
4. `evaluate_circuit.py`: explicit opt-in `--benchmark-generation-checkpoint-dir` plus a positive `--benchmark-stop-after-generation-batches N` (count newly executed batches across phases). Catch the dedicated exception at the evaluation entry boundary, record `segment_complete`, and exit with a documented code distinct from full success/failure. Completed files remain usable on ordinary failures too. A new one-use segment wrapper/receipt authorizes each job and catches the same status; the old consumed guard is not reset.

## On-disk identity and records

Use `<checkpoint-dir>/<run-fingerprint>/<dataset>/<phase>/manifest.json` and `batch-000000.json` etc.; avoid dataset-name sanitization collisions by including the dataset digest. One atomic JSON per batch is sufficient at these cohort sizes. Write unique temporary file, flush/fsync, `os.replace`, fsync directory. Treat an uncommitted temporary file as absent. Save failures stop the segment: continuing silently would spend generations without protection.

The run/phase manifest must bind:

- Schema/algorithm versions, reviewed source commit **and relevant source-content hashes** (generation, model/compatibility, benchmark preprocessing, mask/donor construction); checkpoint implementation revision; frozen cohort and mask artifact SHA256; ordered five-state names and exact effective state mask digest; dataset/phase identity.
- Ordered recipient and pool item records/IDs, rendered prompts, historical selection provenance, pairing/partner-index vectors; separately preserve historical A40 provenance and fresh H200 execution provenance. For donor phase, the exact ordered `missing` list and recipient dependency digest.
- Exact encoded clean IDs, attention mask, corrupt IDs and their shape/dtype/content digests; prompt width; tokenization/chat-template/model-config identities; resolved immutable model/tokenizer revisions (or existing verified weight-file bindings), not merely an alias.
- Runtime model dtype, GPU model/compute capability, torch/transformers/CUDA and relevant attention/backend settings; model eval mode; seeds including training/global, screen, wikitext/null where present; greedy policy, cache mode, sorted EOS IDs, pad ID and **resolved** `new_tokens`; fixed batch size and ordered original batch row indices/trim widths. Record per-segment hostname/GPU UUID/job ID as provenance, not identity: another matching H200 must be usable. Reject A40/A100 or software/dtype drift.

Each batch record contains schema, run+phase digest, batch ordinal, exact original row indices, input-slice digest, `keep/cut`, generated shape `[batch_rows, resolved_new_tokens]`, integer token IDs in original batch order (including EOS and post-EOS pad), payload checksum and producing segment/job provenance. Validate all fields, token range and token count before use; reject duplicate/foreign rows, bad hashes, impossible plans and corrupt committed files. Explicit checkpoint reuse with any identity mismatch **fails closed**, rather than silently discarding paid progress and regenerating. Never merge different namespaces automatically.

A complete manifest is advisory; completeness is derived from every required original batch existing and validating. Reconstruct `torch.long` outputs by concatenating saved generated blocks, restoring the existing inverse order, and attaching the freshly verified original clean IDs exactly as stock code does. Do not round-trip through decoded text.

## State/coherence save boundaries

A restored screen is still the same frozen cohort: fresh intact failures remain included, no re-screen/refill or eligibility change. Keep all five states requested even when only some have finished. An incomplete segment is not an efficacy result.

The batch store alone prevents repeating completed **generation**. To avoid repeating whole completed configs, add an atomic state-result sidecar **after** `_run_config` has finished judging **and coherence**, with generation-token digest, judge/rubric/cache-policy identity, coherence implementation/settings/reference-model identity and the returned cell. On resume validate that identity and cell coverage, then skip the finished state; retain the existing block JSON write. Do not trust current text-only partial JSON as a checkpoint. Judge cache and USD ledger retain their current independent billing semantics; retries must still use the budget guard.

Minimal coherence boundary: rerun coherence for the one interrupted state from saved exact tokens. Existing `coherence_metrics` can remain unchanged; this repeats some reference forwards but no generation or cached paid judgments. If runtime measurement later shows that insufficient, row-chunk coherence checkpoints can store NLL sums/token counts and distinct-n inputs; this is optional follow-up, not necessary for batch generation resume. Do not imply the minimal design saves every interrupted coherence forward.

## Tests and operational limits

CPU/tiny-model tests: uninterrupted versus stop/resume across recipient, donor and masked phases, exact raw-token and final order equality; equal-length stable ties, ragged prompts, last short batch, early EOS/pad handling; full-state recipient reuse; identical donor list/assignments and corrupt tensor; zero `generate` calls for loaded batches; interrupted temporary write versus corrupt committed file; refusal for changed cohort/order/donor assignment/mask/source/model/H200 identity/dtype/backend/seed/token limit/EOS/cache/batch size; mismatch even when all batches loaded; writer collision and stop only after durable commit; complete state skipped while incomplete coherence reruns; unchanged non-opt-in behavior. Run relevant tests in both supported environments, with one bounded H200 split-vs-uninterrupted technical proof before production, under root's receipt/budget.

This design intentionally does not save KV caches or partially decoded batches. At ~1.9 steps/s a capped 1024-step batch alone costs ~9 minutes; choose a segment duration with model-load + one complete batch + save margin, and check a monotonic deadline before starting another original batch. A killed in-flight batch can still be lost. **The currently running old-source first batch cannot acquire this feature retrospectively**; stdout progress is not raw token evidence. Do not promise recovery of its RAM after exit. Future completed batches survive segment exits once this seam is implemented and reviewed.
