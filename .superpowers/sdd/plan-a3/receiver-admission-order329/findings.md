# Receiver proof and admission order

Status: handed-back. Read-only dependency findings, not a scheduling decision or authorization.

There is an operational ordering obstacle under the currently accepted workflow, but no inherent lower-reader/model-authority code cycle. The bare receiver can measure data before a pilot admission exists. The native pilot must begin with completed receiver evidence already anchored in its original immutable root objects. Source has no sbatch/hold/release gate; accepted scheduling policy supplies the earlier gate. Keeping spend within the existing cap does not by itself waive that policy.

## Existing order

The accepted design's `decision-and-scope.json` recommended_order ends: “Only after measured paired feasibility and fresh ordinary root authority may any A3 GPU reservation be proposed.” Its `measurement-and-budget.json` paired_dependency requires a defensible conservative paired bound before first timing spend, **or a separately approved sequencing/budget decision**. Its descriptor contract explicitly calls receiver proof a separate immutable measurement reference anchored in the **later root admission**. These are the relevant specific statements; they do not make profiling depend on an already completed copy of its own proof.

The root approval/anchoring in that scheduling sentence is distinct from the process-local _AuthorityContext: the latter can only be minted after actual live allocation validation. A held pending job provides an ID, not an allocated host on which to perform genuine receiver measurements. Holding a job is not an exception to the earlier reservation gate or the reserved-hour charge. The native code does not specify an independent pre-submit/pre-release receiver check because it does not submit/release jobs.

## Hard native order

1. `_read_prepared_target_object` is data-only. Accepted278-r2 receive_native invokes it plus a final witness for cold and same-process warm trials, without calling the authority loader. Root must authenticate source/allocation/software/storage and actual new-executable provenance externally.
2. Root must finish the measurement run/resource record and original producer refs before first-time anchoring in `a3_root_pilot_admission_v1.pilot_target_preparation`. The execution reservation binds that admission's exact bytes/hash, and the original mapping anchors its reference/lineage. This is not the downstream `prepare --action admit` command, which requires completed pilot receipts and emits a cost proposal.
3. Production pilot dispatch first runs model_guard: fresh source/protection/ledger/reservation/actual allocation/budget/lease validation mints the live _AuthorityContext. Its witness seals original admission/reservation/mapping objects. Starting this path with an incomplete admission and adding resources afterward fails immutable byte/lineage checks; no adopt-current repair is allowed.
4. `load_prepared_pilot_target` demands the completed receiver resource reference, normal run/source provenance, exact actual consumer context and capacity before the large read. It checks actual reader resources, reconciles process/cgroup scopes, rechecks live context and charges the genuine handle before returning. Another model_guard and actual Slurm/CUDA check precede the original model loader. Full original numerical controls and final proof/publication still follow.

Source pointers are enumerated in `dependencies.json`, especially runtime dispatch, validate_reservation, _AuthorityContext, _prepared_binding and load_prepared_pilot_target. No successful scheduler release substitutes for any of those checks.

## The proposed same-allocation combination

Source does not intrinsically prohibit CPU-only profiling operations at the start of a GPU-resourced allocation, followed by normal pilot entry after root has accepted proof and created its complete immutable root objects. This would not inherently require changing production source. It would require an explicit reviewed sequencing decision and reviewed truthful orchestration; current CPU-only authorization does not grant it. Do not disguise a GPU allocation as a CPU allocation or bypass a CPU-only supervisor's GPU rejection.

All profiling/waiting/publication/import/guard/model work must retain the original allocation/wrapper clock and tightened deadline. The original specificity_a3.sh unconditionally overwrites A3_WRAPPER_START_SECONDS at invocation; launching that shell after diagnostics would reset native startup accounting. A separately reviewed combined orchestration must preserve the earlier clock into unchanged native dispatch rather than assume the original shell inherits it. The two profiling trials perform six target read/hash passes; unchanged production entry plus its final witness then performs three more. The profiled graphs are dropped by the accepted adapter, and cannot be reused as loader-minted handles. Account at least those nine passes and three parse/freeze entries, plus ordinary extra references/guards, actual numerical work, model startup and terminal costs. Do not count diagnostic profiling as the actual production entry or erase it from GPU billing.

The direction M1 allowance is a **pair**, not an initial-job allowance. Reserved hours remain charged despite actual underuse, cancellation or failure. Reserving the whole half GPU-hour for a first diagnostic/prefit allocation leaves no later reservation room for selected timing. Selected timing still depends on real M2 and complete CPU selection, with its own inventory/reservation scope; do not assume it can share or retarget the first reservation. No reduction of controls, resource tiers, final barrier or selected dependency is allowed.

Therefore the source answer is conditional, not an approved escape: the combination could only be considered after the explicit sequencing decision and only if all original resource/numerical/authority/time gates pass before model access. No claim is made that it fits the pair, that receiver/handle bounds can yet be accepted, or that producer/source prerequisites are complete. If a gate fails, model access stays blocked and the original reservation charge remains. Root decides whether to seek such a sequencing decision; this audit requests no job, spend, cap amendment or new implementation.
